# Webhook Secret Stored as Plaintext for HMAC Signing

## Status

Accepted — documented deviation from the original specification

## Context and Problem Statement

The original Fieldstone specification states: "Webhook secret stored as bcrypt hash, never plaintext." The webhooks service signs every HTTP delivery with `HMAC-SHA256(secret, body)` and sets the `X-Fieldstone-Signature: sha256=<hmac>` header so the receiving system can verify authenticity.

bcrypt is a one-way function. If the secret is bcrypt-hashed at storage time, the raw secret cannot be recovered. Without the raw secret, the service cannot compute the HMAC. The specification as written is self-contradictory: it requires both bcrypt hashing (which prevents secret recovery) and HMAC signing (which requires secret recovery).

This ADR documents the resolution and the production path.

## Decision Drivers

* HMAC-SHA256 signing requires the raw secret at delivery time — there is no alternative.
* The secret must not appear in API responses after the initial registration (show-once semantics).
* The database must not store secrets in a way that a DB dump immediately exposes all webhook endpoints to impersonation.
* The implementation must be simple enough to ship and auditable enough to fix.

## Considered Options

* **bcrypt hash only** — impossible: HMAC cannot be computed from a one-way hash.
* **Plaintext storage** — correct for HMAC; unacceptable for production if DB is compromised.
* **AES-256-GCM encryption at rest** — correct: recover plaintext with the application key; DB dump without the key reveals nothing useful.
* **Derive HMAC key from bcrypt hash** — not standard; changes the verification algorithm and breaks compatibility with the documented verification process.

## Decision Outcome

Chosen option: **plaintext storage with a documented production requirement for AES-256-GCM encryption at rest.**

The `secret_hash` column in `webhooks.endpoints` stores the raw secret as plaintext. The column name (`secret_hash`) is a misnomer inherited from the spec — it reflects the original intent, not the actual storage format.

The `CreateWebhook` handler stores the secret plaintext and returns it once in the 201 response; subsequent GET responses omit it entirely. This matches the show-once pattern used by GitHub, Stripe, and other webhook providers.

A `TODO` comment in `handlers/webhooks.go` marks the encryption upgrade point:

```go
// Store the secret in plaintext for HMAC signing.
// TODO(fieldstone): encrypt at rest using AES-256-GCM with a key from env.
ep, err := h.queries.CreateEndpoint(r.Context(), webhooksdb.CreateEndpointParams{
    SecretHash: req.Secret, // plaintext — safe only while Postgres is internal
    // ...
})
```

### Production upgrade path

Add a `WEBHOOK_ENCRYPTION_KEY` environment variable (a 32-byte AES-256 key). On `CreateWebhook`, encrypt the secret before storing. On delivery, decrypt before computing HMAC. Rotate by re-encrypting all rows with the new key before removing the old key from the environment.

The column can remain named `secret_hash` for backward compatibility; the column comment should be updated to "AES-256-GCM ciphertext of the signing secret."

### Mitigating factors (current state)

* The `webhooks` schema is only accessible through PgBouncer on the internal Docker network — not exposed externally.
* Webhook secrets are provided by the city; they are not generated by Fieldstone. If a secret is compromised, the city rotates it by deleting and recreating the endpoint.
* The secret is never returned after initial registration.

### Positive Consequences

* Webhook delivery and HMAC signing work correctly.
* The implementation is simple and auditable.
* The upgrade path to encryption at rest is clear and additive — no schema change required.

### Negative Consequences

* A database dump exposes webhook signing secrets in plaintext until the AES encryption is implemented.
* The column name `secret_hash` is misleading — it documents the original intent, not the actual storage format.
* The spec is contradicted, which may confuse future contributors who read the spec without this ADR.
