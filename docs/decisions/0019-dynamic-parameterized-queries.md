# Dynamic Parameterized Queries for Optional Filters

## Status

Accepted

## Context and Problem Statement

The audit query API (`GET /v1/audit`) supports four optional filter parameters: `event_type`, `source_service`, `from`, and `to`. Any combination of zero to four of these may be present in a request. sqlc requires queries to be written as static SQL — it cannot generate a query that optionally includes or omits WHERE clauses based on runtime conditions.

ADR-0006 established "sqlc only — no `fmt.Sprintf` into SQL, no string concatenation into queries." How should optional filter parameters be implemented without violating that rule?

## Decision Drivers

* Optional filters must not be implemented with 16 separate static queries (one per filter combination) — that is unmaintainable.
* User-supplied values must never be interpolated into the SQL string — parameterized binding is non-negotiable.
* The solution must be readable and auditable by someone unfamiliar with the codebase.
* The pattern must be clearly distinguished from unsafe SQL string building.

## Considered Options

* **Static queries for every combination** — 2^4 = 16 queries; unmaintainable; ruled out immediately.
* **Single permissive query using `COALESCE`** — `WHERE ($1::text IS NULL OR event_type = $1)` allows NULL to mean "no filter"; works with sqlc, but PostgreSQL cannot use indexes efficiently on these OR conditions.
* **Dynamic query builder with positional parameters** — construct the WHERE clause programmatically; user values go into a `[]any` args slice and are referenced as `$1`, `$2`, etc.; `fmt.Sprintf` is used only to write the argument index.
* **ORM/query builder library** — introduce a library like `squirrel`; adds a dependency and violates the sqlc-only spirit.

## Decision Outcome

Chosen option: **dynamic query builder with positional parameters**, because it produces efficient SQL with proper index use, keeps all user values in the parameterized args slice, and the code is easy to audit for injection safety.

The `fmt.Sprintf` call interpolates only the argument *index* (an integer computed by the Go code), never user data:

```go
func buildListQuery(countOnly bool, params ListEventsParams) (string, []any) {
    args  := []any{}
    where := []string{}

    if params.EventType != nil {
        args  = append(args, *params.EventType)
        where = append(where, fmt.Sprintf("event_type = $%d", len(args))) // $1
    }
    if params.SourceService != nil {
        args  = append(args, *params.SourceService)
        where = append(where, fmt.Sprintf("source_service = $%d", len(args))) // $2
    }
    // ...
    // User values are always in args. fmt.Sprintf only writes "= $1", "= $2", etc.
}
```

The resulting query is passed to `pgx.Query` or `pgx.QueryRow` with `args...`. pgx handles the binding; the database never sees user values as SQL text.

### Why this does not violate ADR-0006

ADR-0006 prohibits `fmt.Sprintf` into SQL for user values — it is an anti-injection rule, not a blanket prohibition on string construction. The constraint it targets is:

```go
// BAD — user value interpolated into SQL text:
query := fmt.Sprintf("WHERE name = '%s'", userInput)

// SAFE — only the parameter index is interpolated:
query += fmt.Sprintf("WHERE name = $%d", len(args))
args = append(args, userInput)
```

The argument index (`len(args)`) is a Go-computed integer; it cannot carry a SQL injection payload. This pattern is the standard recommendation in the pgx documentation for building optional filter queries.

### Scope restriction

This pattern is used **only** for queries with genuinely optional filter parameters that cannot be expressed as static SQL without unacceptable index-scan degradation. The overwhelming majority of queries in Fieldstone remain static sqlc-generated code. New uses of this pattern require a comment explaining why a static query is insufficient.

### Positive Consequences

* PostgreSQL can use column indexes (`event_type`, `source_service`, `occurred_at`) effectively because the generated SQL includes only the WHERE clauses that apply.
* The audit query API supports all 16 filter combinations from a single code path.
* The pattern is contained to one function (`buildListQuery`) that is easy to audit in its entirety.

### Negative Consequences

* The pattern requires careful review to confirm that user values never appear in the `fmt.Sprintf` call — a future author could accidentally violate this.
* It is not generated by sqlc and therefore does not benefit from schema validation at code-generation time.
* It falls outside the sqlc regeneration workflow; changes to the schema require manual updates.

## Pros and Cons of the Options

### COALESCE pattern

* Good, because it is a single static query compatible with sqlc.
* Bad, because `WHERE ($1 IS NULL OR col = $1)` prevents PostgreSQL from using indexes on `col` — it must evaluate the OR condition for every row, resulting in sequential scans on large tables.

### ORM/query builder library

* Good, because it is explicit about what it is doing.
* Good, because it would handle N+1 and other query patterns too.
* Bad, because it introduces a dependency and violates the sqlc-only convention established in ADR-0006.
* Bad, because the audit service is the only service that currently needs dynamic filters.
