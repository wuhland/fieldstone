# sqlc for Type-Safe Queries, No ORM

## Status

Accepted

## Context and Problem Statement

Fieldstone services need to interact with PostgreSQL. The database access layer choice affects SQL injection risk, query performance transparency, migration ergonomics, and how readable the data layer is for contributors who know SQL but may not know a specific ORM's query DSL.

## Decision Drivers

* SQL injection must be structurally impossible — not just avoided by convention.
* Queries should be readable as SQL, not translated through an ORM DSL that obscures what is actually sent to the database.
* Type safety at compile time is preferred over runtime failures when the schema changes.
* The codebase should be approachable to Go developers who know SQL but have not used Go ORMs.

## Considered Options

* **sqlc** — compile SQL queries to type-safe Go functions; schema changes caught at code generation time.
* **GORM** — full-featured ORM with ActiveRecord-style API, associations, hooks, migrations.
* **ent** — entity framework with code generation from a schema DSL; graph-based query builder.
* **Raw `database/sql`** — standard library, maximum control, no code generation.
* **pgx directly** — use `jackc/pgx` without an ORM, writing queries as strings with typed scan helpers.

## Decision Outcome

Chosen option: **sqlc**, because it provides compile-time type safety from plain SQL without introducing an ORM abstraction. Queries are written in `.sql` files, reviewed as SQL, and compiled to Go functions. `fmt.Sprintf` into query strings is structurally impossible — all parameters go through prepared statement placeholders generated by sqlc.

Each service has its own `db/query.sql` and `db/sqlc.yaml`. The `make generate` target runs `sqlc generate` for all services.

### Positive Consequences

* SQL injection is not possible via the sqlc-generated layer — all inputs are bound parameters.
* SQL queries are reviewable as SQL by anyone familiar with PostgreSQL, not just Go ORM users.
* Schema changes cause `sqlc generate` to fail with a clear error before the code is even compiled.
* There is no ORM magic: N+1 queries, missing indexes, and slow scans are immediately visible in the query files.
* Generated Go code is readable and can be audited without understanding sqlc internals.

### Negative Consequences

* More boilerplate than an ORM for simple CRUD: each query must be explicitly written in SQL.
* Schema migrations and query files must be kept in sync manually (sqlc catches mismatches, but only on regeneration).
* Complex joins or dynamic queries require more thought to express in static SQL.
* `make generate` must be run after any schema or query change — easy to forget during rapid development.

## Pros and Cons of the Options

### GORM

* Good, because it handles CRUD, associations, and migrations with minimal boilerplate.
* Good, because auto-migrations lower the friction of schema changes during development.
* Bad, because the generated SQL is opaque — understanding what a complex query does requires tracing through GORM's internals.
* Bad, because GORM's auto-migrations are not safe to run in production without review.
* Bad, because it is easy to accidentally produce N+1 queries through lazy loading.
* Bad, because `db.Where("id = ?", userInput)` still requires trusting the developer to always use placeholders.

### ent

* Good, because the schema is defined in Go code and the graph-based API prevents many query mistakes.
* Good, because it generates type-safe predicates.
* Bad, because the schema DSL is non-standard and has a steep learning curve for developers new to ent.
* Bad, because the generated code is voluminous and hard to audit.

### Raw `database/sql` or pgx

* Good, because there is no abstraction between the developer and the database.
* Good, because every query is explicit and reviewable.
* Bad, because scan boilerplate is significant and error-prone (forgetting to scan a column, scanning into the wrong type).
* Bad, because there is no compile-time check that queries match the schema — schema changes produce runtime panics.
